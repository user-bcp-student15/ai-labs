# HU-01 — Validar en la API el JWT emitido por auth

## Origen
- `H-API-01 (api)`, “El verificador de API no acepta el JWT firmado de auth y no verifica firma”, estado `Pendiente` en `HALLAZGOS.md`.
- Evidencia registrada: `api/app/main.py:14,17-26`; el hallazgo también referencia el JWT emitido por auth y enviado por web.

## Historia de usuario
Como persona autenticada, quiero que la API verifique el token JWT emitido por auth antes de usar su identidad, para que las rutas protegidas no acepten identidades no verificadas.

## Contexto actual y problema confirmado
Auth emite un JWT HS256 con los claims `sub`, `role`, `iat` y `exp`; web lo envía en el encabezado Bearer. El verificador de API espera el formato Base64 legado y no valida una firma criptográfica. Por ello, el flujo de login no interoperaba con la API y la identidad no quedaba autenticada criptográficamente.

## Comportamiento a preservar
- `POST /auth/login` conserva su contrato observado: status y forma JSON de éxito, algoritmo, claims y vigencia actuales del token.
- La web continúa enviando el token mediante `Authorization: Bearer`.
- `GET /api/tasks` y las demás rutas que comparten la dependencia de identidad conservan sus respuestas exitosas actuales para solicitudes autenticadas.

## Alcance
- Validar en el límite de autenticación de la API la firma, expiración e identidad del JWT emitido conforme al contrato actual de auth.
- Comprobar el flujo integrado de login a `GET /api/tasks` y las rutas existentes que comparten la dependencia de identidad.
- Obtener la clave de validación desde configuración externa; las pruebas usan únicamente una clave ficticia.

## Fuera de alcance
- Cambiar los claims, algoritmo, vigencia o respuesta de `POST /auth/login`, o modificar el envío del Bearer desde web.
- Cambiar autorización por propietario, consultas SQL o carga de archivos.
- Decidir la compatibilidad con consumidores del formato legado sin confirmar primero si existen fuera de web.

## Criterios de aceptación verificables
1. Con credenciales ficticias válidas, el JWT emitido por `POST /auth/login`, enviado como Bearer a `GET /api/tasks`, se acepta solo después de verificar firma y expiración. **Verificación:** prueba integrada que comprueba el status y la forma de respuesta caracterizados, y que la identidad usada por la ruta procede del token verificado.
2. Un token malformado, alterado o expirado enviado a `GET /api/tasks` recibe `401` y no obtiene una respuesta exitosa. **Verificación:** una prueba por cada caso.
3. Las demás rutas existentes que comparten la dependencia de identidad aceptan un JWT válido y mantienen su status y forma de respuesta exitosa. **Verificación:** pruebas funcionales de esas rutas.
4. El cambio no altera el contrato exitoso de `POST /auth/login`, incluidos los campos `token`, `expiresIn`, `user` y `debug`, ni los claims y la vigencia actuales. **Verificación:** pruebas de contrato de auth antes y después del cambio.
5. La clave de validación se proporciona externamente y no se incorpora al repositorio; las pruebas no usan secretos reales. **Verificación:** revisión de configuración y ejecución con una clave ficticia suministrada al entorno de prueba.

## Contratos afectados/protegidos
- Protegidos: `POST /auth/login`, el encabezado `Authorization: Bearer` y las respuestas exitosas existentes de las rutas protegidas de la API.
- Afectado: autenticación de `GET /api/tasks` y de las rutas que comparten la dependencia de identidad.

## Riesgos, supuestos y preguntas abiertas
- Se asume que la API puede obtener de forma segura la misma clave de firma que usa auth; falta confirmar el mecanismo exacto de configuración para ambos servicios.
- Confirmar si existen consumidores del formato legado fuera de web antes de decidir su rechazo y cualquier transición.
- El cuerpo de error `401` de la API no está fijado como contrato; confirmar si debe preservarse.
- Una clave ausente o distinta entre servicios puede impedir la interoperabilidad; verificar el flujo integrado con una clave ficticia configurada externamente.
